# 双臂扩展接口

为未来接入第二台 X5 预留的接口。当前硬件和内核都是单臂，本文说明已经就绪的部分、接入双臂时还需要补的环节，以及唯一的判定规则。

## 已就绪

### 状态接口

`GET /api/v1/system/status` 新增 `arms` 数组：

```json
"arms": [
  {"id": "arm1", "label": "机械臂", "joints": [0, 0, 0, 0, 0, 0], "velocities": [0, 0, 0, 0, 0, 0]}
]
```

- 由内核的 `q` / `dq` 按每臂 6 个关节切分得到（`src/embodied/applications/console/transport/system.py: arm_views`）；
- 单臂时长度为 1，`label` 为「机械臂」；
- 上报 12 个关节时自动变成两条：`arm1` / `arm2`，标签为「机械臂 1 / 机械臂 2」；
- 旧的 `q`、`dq`、`pose`、`gripper_*` 字段原样保留，现有调用方不受影响。

### 页面

- **总览**：关节区按 `arms` 渲染，几臂就几组；双臂时每组前出现臂名标签。
- **采集**：关节曲线列表按 `arms` 动态生成，行数与分组随臂数变化；单臂时为 6 行，与原来一致。
- **控制台**：状态栏出现「机械臂 1 / 机械臂 2」选择器（单臂时隐藏）。选择后，关节面板、3D 场景都显示该臂的数据；关节类命令（`move_joint` / `reset_joint` / `move_joint_target`）在多臂时自动带上 `arm` 字段。
- 三页都对 `arms` 缺失做兜底（当作单臂 6 关节），静态预览和旧后端下不会报错。

### 唯一的判定规则

```
臂数 = len(q) // 6     （q 长度必须是 6 的整数倍）
```

页面不做其他假设，也不读取硬件配置。

## 接入双臂时还需要补的

按依赖顺序，这些目前仍是单臂语义：

| 环节 | 现状 | 双臂需要 |
| --- | --- | --- |
| 内核 / 驱动 | 一个内核进程控制 6 关节 | 12 关节的 robot 驱动，或两个受管实例；`describe()` 返回 12 项限位 |
| 姿态 / 夹爪 | `pose`、`gripper_width`、`gripper_effort` 为单臂标量 | 按臂返回，并放进 `arms[]` 各自字段 |
| 控制页 | 已有臂选择器，关节面板与 3D 显示所选臂；命令带 `arm` 字段 | 双模型同屏场景、末端位姿/夹爪按臂显示、目标编辑按臂隔离 |
| 采集 | `capture` 记录单机器人的 state 流 | episode schema 按臂拆分（如 `state.arm1.*`），训练维度与 action horizon 同步扩展 |
| 工作台 profile | `real-quest` / `real-manual` 单臂 | 新增 `real-dual-*` 配置，现有一律保持单臂 |

## 验证方式

- 单臂：现状不变，`arms` 长度 1，页面与改造前一致。
- 双臂：拦截 `/api/v1/system/status`，返回 12 个关节与两条 `arms`，页面应出现 12 行曲线和两个分组标签；已在开发中按此方式验证通过。
- 单元测试：`tests/motion/test_console_status_endpoint.py::ArmViewTests` 覆盖 6/12 关节与空反馈三种情况。
