**当前实现边界（2026-10-22）**

公共控制运行时已迁入 `src/embodied/control/`：网关、命令调度、worker、IPC 和 observer 共用一份实现。ARX 型号参数、SDK、真机/仿真后端与运动学在 `src/embodied/devices/robots/arx5/`，Quest 原生输入与路由在 `src/embodied/devices/inputs/quest/`。设备适配按硬件组织，公共运动、数据和策略能力按职责组织；模块目录不等于进程数量。

- 唯一插件目录为 `configs/plugins.json`。装配层按 profile 选择工厂；驱动拥有 preflight、资源标识、能力、关闭策略和模型快照元数据；诊断、viewer 和路由由注册表选择，输入配置惰性读取。公共 runtime 不拥有某品牌的特殊配置解释器。
- 参数位于 `configs/robots/`、`configs/inputs/` 与 `configs/control/`；控制环境声明在 `configs/environments/control/`，安装结果在 `outputs/envs/control/`，运行记录在 `outputs/runtime/control/`。
- `third_party/` 为只读参考，不从中导入模块、查动态库、启动模型或安装环境。正式依赖锁版本；受管安装工作区在 `outputs/dependencies/`，维护的 vendor 源码保留来源与许可证。
- 当前遥测是 RobotTick V3：显式关节数与 15 轴容量，JSON 仅包含实际轴数；episode schema 2 仍表示 MCAP 存储和动作语义。当前完整后端仍是 X5；LeRobot X5 导出器明确拒绝非六轴记录。
- 本轮参考了 [PhyAgentOS 的能力声明与生命周期设计](phyagent-reference.md)，未引入其运行依赖，也未宣称获得新的机器人驱动。

**目标是每个部件可以单独理解、替换、验证和优化。** 全部代码归入 ThoughtIntoAction；arx-televr 的完整遥操链路先按原组织复用。首轮将它作为边界清晰的控制单元，使用已有入口和配置；外围按功能拆分，后续有具体优化需求时再深入它的现有模块。

**插件粒度校正：** arx 原版已经具备 VR 设备、模式协调、遥操路由、IPC 桥接、目标控制器、机械臂后端与只读显示的边界。插件化直接对应这些职责，组合启动交给装配层。本轮已拆为设备进程工厂、原生路由装配、worker 命令入口、租约会话，并补齐 real/sim 的目标控制器注入；详见 [源码复核与实施结果](arx-component-review.md)。

模块边界与进程边界分别决定。算法、求解、文件读写可以是库；机器人周期、原生 XR、相机、采集写盘和 GPU 推理由时序、故障或依赖隔离决定进程。先保留已有进程结构，再按测量增加隔离。下表的模块不要求各自成为服务，也不要求一次性建立所有目录。

**功能部件与状态所有权。** 每个部件只维护自身状态，其他部件通过明确的快照、事件或请求获得信息。

| 部件与建议位置 | 输入、输出 | 拥有的状态 | 独立运行或验证方式 |
| --- | --- | --- | --- |
| 公共控制 `src/embodied/control/` 与设备 `src/embodied/devices/robots/` | 原生输入或 RPC 命令；反馈、提交结果与状态事件 | runtime 拥有周期、命令与 owner；设备拥有 SDK 和型号控制状态 | 模型/profile fixture、MuJoCo 与设备适配对照 |
| 设备输入 `src/embodied/devices/inputs/`、`apps/ios/` | 原始帧/按键；映射后的目标或操作事件 | 设备 session、追踪状态、离合锚点、mapping profile | 协议金样本、输入回放与 Ghost；不需要真机械臂 |
| 运动操作 `src/embodied/applications/operations/` | 点动、计划、执行、取消；计划文件、进度与结果 | 操作生命周期、计划身份；worker 拥有执行进度的权威状态 | 固定起点/模型的离线规划与仿真执行 |
| 传感器 `src/embodied/devices/sensors/` | 设备数据和显式启停请求；原始帧、内参、诊断 | 设备连接、stream epoch、帧序号、使用租约 | 录制文件或合成帧替代设备；相机可单独运行 |
| 观测对齐 `src/embodied/data/alignment/` | 有时间和身份的状态/图像；有效观测或缺失原因 | 有界时间窗口，无设备所有权 | 固定时间序列验证帧选择、年龄与缺口 |
| 采集 `src/embodied/data/capture/` | 机器人/相机流、按键事件；episode 和任务状态 | 录制起止、任务计数、缓冲、失败原因 | 合成流或回放流录制，不需要 Quest/CAN |
| 数据文件 `src/embodied/data/episode/` | 版本化记录；MCAP、视频、元数据的读写 | 文件句柄、提交状态、完整性索引 | 小型历史/新版 fixture 读写和中断恢复 |
| 数据处理 `src/embodied/data/export/` | 已封存的数据；校验、标注、打包、LeRobot 数据与统计 | 离线任务和转换规则 | 没有控制/相机环境的批处理 |
| 手眼标定 `src/embodied/applications/calibration/` | 计划、原始 RGB、模型反馈；采样会话与外参 | 标定流程、样本划分和结果 | 合成真值、历史样本离线求解；动作经 operations 接入 |
| 策略 `src/embodied/policy/`，保留现有推理后端 | 带身份的观测、任务、模型配置；明确语义的动作块 | 模型、预处理/统计、推理请求 | 录制观测输入、无动作预测、仿真 rollout |
| 监看与回放 `src/embodied/applications/monitor/` | 公共状态/历史记录；页面、趋势、Ghost | 显示与播放游标 | 无设备的历史回放；关闭页面不影响生产者 |
| 装配与维护 `src/embodied/applications/workstation/`、`scripts/` | 启动选项和配置；进程组、连接准备与状态 | 进程身份、依赖关系、启动结果 | 配置解析、只读诊断、缺少可选组件时的启动检查 |

`operations` 负责通用的计划/执行/取消；标定的“到位后采图”、采集的任务流程和策略的“观测后预测”各自归功能模块。工作台可以装配完整工作流，但不把所有功能状态机集中到一个 manager。

**依赖方向需要能被自动检查。** `contracts/` 保存跨环境的协议说明、schema 和金样本；`runtime_client` 实现传输与客户端；领域算法与工作流仅依赖自身所需的窄接口。协议规范不要求共享同一份 Python 对象，更不能跨环境传递 SDK、MuJoCo 或可变 NumPy 引用。

- control 不导入 collection、monitoring、handeye_calibration、policies 或 datasets。工作台的客户端通过协议访问控制单元。
- 设备驱动不导入采集/标定/推理业务。相机只知道租约、流配置和帧，不查询任务名或遥操内部状态。
- episode_io 不导入控制、输入 SDK、GUI 或 LeRobot；datasets 和 collection 都可使用它，互不导入各自业务状态机。
- 标定求解器不导入设备客户端；标定执行适配才依赖 operations、相机和反馈接口。策略模型后端不获得 CAN 客户端。
- UI 的只读订阅与操作客户端分开。打开监看、历史回放或帮助命令，不隐式获取运动控制权；设备启动是显式的装配操作。
- `robot_core` 逐步缩减为无业务状态的基础设施，不继续加入采集、预抓取和策略流程。已有旧功能由兼容层保留到对应迁移完成。

当前使用轻量注册表和小型 Protocol 表达插件边界，不建立复杂继承树；跨进程边界用版本化消息。现有注册表在装配层选定实现，各部件不自行搜索插件或读取全局配置。

**公共契约按首次使用时间逐个建立。** 首轮使用上游原契约；阶段二增加遥测与帧契约，阶段五增加操作和策略契约。

| 契约 | 必须明确的内容 | 消费规则 |
| --- | --- | --- |
| RuntimeDescriptor / RobotTickV3 | runtime/boot 身份、模型与实际配置、字段有效性、序号与独立时间 | 描述握手后消费；记录缺口；采集完整流与监看最新值分开 |
| InputFrame / InputEvent | 设备 session、唯一帧序号、追踪有效性、时钟域、按键边沿 | 不用重包刷新年龄；姿态可只取最新值，离散事件去重且定义缺失行为 |
| CameraFrame | camera/stream 身份、帧序号、分辨率/编码/颜色顺序、内参及畸变模型、设备/主机时间 | 标定和采集读原始图；预览压缩图另行提供；丢帧不可被新序号掩盖 |
| Observation | 选中的 frame/tick ID、各自时间与年龄、对齐规则、有效性 | 不同业务传入不同要求；训练锚点、在线推理和静止标定不强行共用一个选帧公式 |
| MotionPlan / OperationStatus | 起点约束、模型/profile、owner、计划哈希、允许的终止行为、状态与错误码 | 预览和执行同计划；accepted/running/completed/cancelled/failed 有明确含义 |
| PolicyActionChunk | request/observation 身份、模型/统计版本、action_definition、采样周期和有效期 | 晚到结果、旧 owner、过期观测对应的动作被拒绝；不能依靠心跳给旧动作续期 |
| EpisodeManifest / CalibrationResult | 各自 schema、文件完整性、来源、模型/frame/config 身份 | 原始结果不覆盖；派生结果保留来源；标定结果不因文件存在而自动启用 |

跨边界统一 SI 单位并明示关节顺序、四元数分量顺序、坐标系与变换方向；上游不同格式在适配边界转换。记录 host monotonic 的 boot/domain 身份；设备或手机时钟保留原值与同步质量。不同 boot 的 monotonic 不能直接比较，回放保留原时间且使用独立播放时钟。

协议 major 不兼容时明确拒绝；可兼容的可选字段通过能力和有效性声明处理。硬件命令遇到未知动作/能力不能静默忽略。每种请求定义最大消息/队列大小、超时、重试及幂等规则。首次只实现当前需要的类型，不先建一套覆盖所有机器人的消息系统。

**配置和模型也是部件接口。** 除源码依赖，还要避免各部件通过文件或环境变量共享隐式状态。

1. 机器人配置选择 `robot_profile` 工厂，ARX 的 robot/tool 参数由设备适配器解析；Quest 配置随输入模块维护。工作台配置按 camera、collection、policy、storage、UI 分域；装配层明确选择文件和 profile，禁止把全局可变配置字典传入所有部件。
2. 解析结果带来源和哈希；启动保存最终有效值与后端读回，不只保存文件名。变更规则区分“立即生效”“重新建锚点”“新 episode”“重建 runtime”；具体规则随功能实施，未声明的控制变更不热更新。
3. 模型仍由 arx 的单一生成流程产生。产物 manifest 包含 source/tool/生成器哈希、关节顺序与限制、frame 定义及单位；控制、Ghost、标定和导出选择同一个版本。独立进程可以各自加载模型，但可变 IK/MuJoCo data 不共享。
4. 工作台的离线 FK 可以使用现有 Pinocchio 环境，但必须读取同源产物，并与 arx FK 做 frame/关节对照；不要求把工作台数值依赖装进控制环境。
5. 标定、模型/tool、观测预处理和策略统计分别保存 revision。依赖变化使相关计划或结果失效，有效性由使用者检查，不用一个全局 `calibrated=true` 代替。
6. 采集保存分部件的源码/原生资源/配置身份。现有 fingerprint 只扫 `src/`、Python 脚本及少量锁文件，迁移后必须纳入 `src/embodied/control/` 与设备模块的实际源码、原生文件与模型；同时区分控制改动与只改监看样式，方便解释对照实验。

**相机与观测需要完成已有解耦。** 当前默认插件已经使用 SharedCamera 和单个 camera-service，应直接复用。后续订阅区分“查看最新画面”和“需要完整帧序列”；当前 latest frame 轮询不能自动升级成无丢帧保证。可先保留轮询并检测缺口，实测需要时增加有界原始帧缓冲，不先引入大型图像总线。

采集、自动标定和策略声明自己的相机使用租约。只读监看不阻止它们工作；活动消费者要求稳定的分辨率/内参，普通关闭或重配置应被拒绝或经过显式结束流程。设备故障则发布流终止，消费者各自决定处理：采集标记失败，标定/视觉策略终止其运动流程，普通 Quest 遥操可继续。租约与帧有效性分别检查，租约存在不代表图像新鲜。

**模式、控制权、停止和故障按职责处理。** 控制端始终做最终命令检查，规划器的预检查不能代替执行端检查；新增工作区/轨迹检查属于执行端的明确能力，不插入第二个控制循环，也不改变首轮 arx 普通跟随。

- 运动命令、夹爪、Home、模式变更由当前 owner 提交。操作取消只取消其自身 operation，不等同于停止整个运行。
- 本机操作员的受控停止和 supervisor 故障停止不依赖当前 owner 续租；由独立的授权管理入口送达，优先于普通目标并清除待执行动作。其他来源不能仅凭“已连接”取得管理权限。它是软件停止请求，不冒充硬件急停。
- 启动、新来源接管和故障恢复分开；不因为重连、心跳恢复或 UI 重开而自动恢复动作。沿用 arx 停止锁存，恢复需要明确的状态检查。
- 阶段零至四保留 Quest 输入/路由故障结束控制组的规则；多源阶段按活动来源声明必需组件。未获控制权的手机断线不停止 Quest，未活动的 Quest 输入退出也不应直接结束手机控制。
- observer 故障不直接修改普通遥操模式；依赖它反馈的自动操作由该操作的失效规则终止。各来源的反馈依赖必须声明，不能笼统承诺“遥测故障永不影响运动”。
- 设备诊断、回零、恢复、test-joint 等维护入口一并纳入设备所有权。运行期维护通过 worker；需要直接 SDK 的离线工具先取得同一设备锁，并拒绝与控制运行共存。

健康状态区分 starting、ready、degraded、failed、stopped。ready 来自真实握手和有效数据，不以 PID、socket 或 ready 文件单独判断。一次运行使用独立的 runtime 身份与 IPC 命名空间；重启清理只处理已确认属于自己的资源。原生 Rollio 全局停止总线的限制仍按主方案记录。

**策略、回放和数据落盘补齐独立边界。** 模型预测只产出动作；预抓取、动作分块执行和接管属于 operations/policy session。统计、动作空间、绝对/增量定义、夹爪单位、训练采样周期必须与当前数据版本匹配；不假设旧模型天然兼容新的 `sent_joint_position` action。保持现有 PyTorch/JAX 环境隔离，模型推理延迟不能阻塞机器人循环。

历史展示、仿真输入回放、真机轨迹重放使用不同入口和命名空间。打开数据只读展示；真机重放需要控制权、重新验证计划与现场起点。合成源和录制输入默认仅进仿真，不能通过统一接口绕过 arx 现有的真机输入限制；新增真机来源在阶段五逐项实现。

采集过程使用未完成状态，结束时排空机器人/相机边界、完成文件写入、校验索引，再原子写入完成 manifest。中断数据可独立恢复检查；缺失区间不能通过重建索引变成“完整”。保留现有写盘与打包实现，先审阅已有能力，再补不足。录像、标注、导出不覆写原始数据；同一个任务的计数和派生数据绑定 episode ID 与版本，重试不能重复计数。

**独立优化的验收需要具体数据。** 复用已有测试和上游检查，按部件改变的行为运行对应验证；文档调整无需运行硬件测试。

| 改动的部件 | 最小对照方式 | 关注指标 |
| --- | --- | --- |
| arx IK/控制局部补丁 | 固定模型/profile、相同输入；原版与适配版分别运行 | 模式与目标差异、IK 残差、周期 p95/p99/max、deadline |
| 手机/输入映射 | 原始包金样本、断流/重连与同一输入轨迹 | 唯一帧率、接收后年龄、目标轨迹、离合/夹爪方向 |
| 规划/操作 | 固定起点和约束，冻结计划，仿真执行 | 端点误差、连续性、时间与关节限制、取消后的残留命令 |
| 相机/对齐/采集 | 固定带序号的状态和图像，注入慢消费者/缺口 | 帧缺口、反馈年龄、对齐结果、完整性与结束边界 |
| 手眼标定 | 合成真值及固定历史采样 | 外参误差、离群点处理、独立验证结果、失效清理 |
| 策略后端 | 固定观测、任务和统计，禁止实机执行 | 输入输出定义、推理时延、过期动作拒绝；再做仿真 rollout |
| 文件读写/导出/监看 | 同一组旧/新 schema 小型档案 | 数据一致性、耗时/内存、设备依赖禁用时可运行 |

增加两类边界检查即可起步：禁止反向导入，以及无设备环境下的启动/离线入口检查。跨 Python/Swift/原生协议用共同金样本；模型用同源 FK 对照。每个部件提供代表性 fixture 和运行说明，测试不依赖开发者同时启动整套系统。

**扩展点以改动范围衡量。** 保留 arx 现有模块作为控制内部边界，外围只依赖公开协议和产物。实现新功能时先写出预计修改范围；如果越过下表范围，先说明新增的真实依赖，避免以“顺便统一”为由改变其他部件。

| 变化 | 正常修改范围 | 应保持的边界 |
| --- | --- | --- |
| 新增一个输入设备 | 输入适配、mapping profile、能力注册与输入测试 | 采集和导出不增加设备专用分支；已有命令足够时不改 IK/SDK |
| 新增一种相机 | 驱动适配、配置、内参/时间契约验证 | 标定和策略仍使用统一帧接口，具体图像预处理保持各自配置 |
| 更换策略模型 | 模型后端、预处理/动作适配、模型描述及验证 | 不将模型框架或统计逻辑放入机器人循环 |
| 优化 IK/夹爪策略 | arx 局部补丁、明确的 profile、算法对照 | 上游版本和原基线保留；变化的控制行为被记录 |
| 优化录像或导出 | 文件读写或 datasets、数据 fixture 与性能检查 | 不修改控制提交和原始动作定义 |

算法本身尽量是显式输入/输出的函数；设备、时钟、存储由边界注入。已有上游状态机保留原实现，只有新接入功能需要的边界才增加适配，不为追求形式统一先拆改 arx。

**耗时操作返回可查询的过程状态。** 控制源切换、Home、轨迹、自动标定和策略任务不能只返回一个成功布尔值。每次操作有 runtime 内唯一的 operation ID，公共状态保留递增 revision 和最近事件序号；UI 重连先查询当前快照，再接续事件，事件缺口通过重新查询处理。

- accepted 表示请求通过入口校验；running 表示执行已开始；completed 需要满足该操作明确的完成条件。轨迹样本已发完不等于机械臂已到位，录制停止接收不等于文件已封存。
- 取消先进入 cancelling；执行端确认已处理待执行命令并达到约定终止状态后才能报告 cancelled。已经进入 C++ SDK 的调用不保证能被 Python 立即打断，停止结果需要分阶段反馈。
- 请求超时或连接中断时，客户端标记结果未知并查询原 operation ID；不能推断“未执行”，也不能创建新 ID 自动重发 Home 或整条轨迹。同一请求 ID、同一内容可在已声明的有效窗口内去重；同 ID 不同内容明确拒绝。
- worker 重启形成新 runtime，旧动作不得自动恢复。工作流可标记 interrupted；设备是否已停止仍需要新反馈确认，不能用业务终态代替物理状态。
- 通用操作状态只描述生命周期；标定样本数量、录制完整性、策略结果作为各功能自己的结果数据。避免重新形成一个包含全部业务字段的状态对象。

**跨部件工作流先准备资源，再开始动作。** 自动标定需要模型、相机、运动能力与计划同时满足条件。用一个小型功能编排器完成检查和资源申请即可，无需增加分布式事务系统。

标定的准备顺序明确为：核对模型/计划及能力，取得所需相机配置租约并确认新帧，申请运动控制权，重新检查机器人反馈与计划起点，然后显式开始执行。资源申请有超时和取消，等待期间不把目标送入 worker。其他组合流程遵循同一资源申请顺序；争用时返回占用者和原因，不无限等待或抢占。

准备失败只释放本操作取得的资源；执行中失败按已定义的终止行为处理，不用自动反向运动“撤销”已经发生的动作。上层编排进程退出后，worker 的 owner 有效期、命令有效期和终止策略仍独立生效。这个流程用于后续常驻控制模式；首轮 arx 真机启动仍保留其显式启动及 Home 行为，不能通过准备资源暗中触发它。

**新算法先做离线和旁路对照。** 为 IK、输入映射和策略保留读取记录数据的评估入口；需要在线对照时，候选算法在独立进程和独立模型状态中读取快照，只输出诊断或 Ghost，没有 SDK、设备锁或运动发布权限。

候选结果记录源输入、反馈、模型/profile 和算法身份，用相同记录对比误差、连续性和耗时。真实反馈仍由原控制器决定，旁路结果不能证明候选算法闭环稳定；后续还需独立 MuJoCo 闭环验证。候选实现超时或退出不影响活动控制，默认关闭，不把额外求解塞入 arx 的 tick。

保留上游控制语义作为对照的一部分。例如 arx 当前可能应用有限且受限位约束的未完全收敛 IK 结果，不能为了统一“成功/失败”字段就悄悄改为完全拒绝。算法质量、命令是否提交和机械臂是否到位分别记录。

**进程隔离之外，给共享资源设预算。** arx 的 250 Hz 对应每周期 4 ms；这是目标周期，不是普通 Linux/Python 的硬实时保证。新增适配记录自己的耗时、队列长度和溢出计数，按未扩展基线和实际负载确定可接受预算。

控制入口每周期处理有界数量的事件和最新目标，协议解析、图像编码、磁盘、模型加载/JIT 及大型规划留在外围。需要处理模式事件和目标先后关系时，以执行端顺序和 ACK 为准；停止优先，不能为了限量处理而排在积压动作后面。该约束先用于新增通道，上游原生链路改变需独立证据。

相机、录像、规划和推理虽然在不同进程，仍共享 CPU、内存带宽、磁盘和 GPU。限制可选计算的线程数、队列和并发，增加“录像 + 推理/规划”的负载对照；CPU 亲和性或调度策略只有测量显示需要时再采用。过载时先降只读预览和诊断的频率；原始数据丢失则明确标记不完整，控制目标过期按失效规则处理，不静默降低控制频率。

因果追踪使用已有身份关联：原始输入/图像、映射目标/预测请求、提交命令和反馈 tick。记录执行端实际采用的输入序号、目标修改/拒绝原因和有效性；基线原生通道尚未提供的关联标为未知，不能用最近收到的样本猜测。字符串格式化和聚合统计放在 observer，tick 只复制必要标量、序号和固定大小字段。

**独立优化后，按验证过的版本组合交付。** 仓库为每个可用版本保存一份静态运行清单：控制源码/补丁、原生 IPC 版本、协议版本、模型/tool、配置、工作台依赖，以及启用时的策略与相机档案。先用现有锁文件和 manifest 表达，无需另建发布服务。

协议能解析只是兼容的一部分；模式、单位、动作定义、停止行为和模型 frame 变化也需要行为验证。升级 arx 时先对照原基线与局部补丁，再运行受影响的部件检查，最后更新清单。回退选择完整匹配的代码/配置/模型组合，不对已经写出的新版原始数据做破坏性降级。

关键决策在对应部件文档用短记录说明：解决的问题、选择、约束，以及什么条件下值得重新评估。当前目录和进程划分已经足够支撑第一轮迁移；进一步抽象由实际第二个调用者、测量结果或明确功能需求推动。

**按主方案阶段落地，避免解耦工程阻塞复用。** 阶段零记录现有入口与保留能力，固定上游；阶段一跑通原 Quest 链路；阶段二随遥测增加最小契约与客户端；阶段三随采集抽出 episode_io 和所需观测对齐；阶段四完成本机适配。阶段五再按依赖分批：

- 5A：控制权、操作状态及必要点动/轨迹执行接口；本机停止、夹爪与退出语义先明确。
- 5B：手机和现有手眼标定分别接入，可独立验收；保留各自设备语义，不互相依赖。
- 5C：示教/运动扩展、真机回放和策略执行按功能恢复；完整默认切换仍受现有能力迁移清单约束。

新接口只在实际调用者需要时建立；已授权目录迁移同步更新调用方，不新增旧路径转发层。每次交付一个能运行、能测量的功能切片，避免一次搬完目录却没有可用入口。
