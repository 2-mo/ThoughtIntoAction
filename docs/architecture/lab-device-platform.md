# 实验室设备接入平台：目标设计

目标是在一台电脑前看见、调用和协同实验室的机械臂、相机、移动机器人与各类传感器。统一工作台承接多模态交互，中央 Agent Harness 组织具身任务，各设备保留独立感知或执行能力，并把实际观测和结果反馈给平台。设计遵循解耦与插件化；它是下一步建设方向，不代表下文所有模块或协议已经实现。

网页的“架构总图”将这份设计与部署位置、物理接线合并展示，“实现进展”保留现有计划与 Git 证据。新增目标不借用旧任务的完成率。当前实现及真机验收边界仍以 [overview.md](overview.md) 为准。

## 总体架构与协作边界

目标体验是“一台电脑控制整个实验室”：用户在统一工作台查看设备、视频与任务，通过网页、终端、语音或手势表达目标并接管控制。中央 **Embodied Agent Harness** 根据上下文和环境状态理解任务、选择技能、调用设备能力，再根据真实观测与执行结果继续或结束任务。感知服务、机械臂运动内核和移动机器人运行时分别持有设备连接与本地执行循环。

统一落在设备视图、能力契约、任务状态、控制权和记录入口上。它不要求把厂商 SDK、不同实时循环或所有设备塞进一个进程。相机、传感器、机械臂和移动机器人共享身份与接口规范；一个物理设备可以同时提供感知和执行能力。

主图按 L1—L8 划分职责：交互呈现 → 应用服务 → 智能编排 → 能力接入与契约 → 推理部署与策略 → 设备运行时 → 驱动适配 → 硬件与设备。每层左侧标明职责，内部模块是可分工的交付单元。模型与数据服务、网络与安全等基础设施放在右侧，并标明服务范围。

层间短箭头表示总体调用方向，另用两条路径标出人工接管与设备反馈；完整接口关系在模块详情中展开。人工与确定性控制可直接调用设备能力，绕过 L3 Agent 和 L5 策略推理，仍经过 L2 用户会话、L4 控制会话及 L6 设备侧校验。策略技能则进入 L5 的观测、异步推理和动作块执行链。观测按订阅接口直接提供给工作台、Agent 或在线策略，不必逐层转发或等待落盘。

这些是逻辑职责层，不是一层一个进程或所有请求必须穿过的网关。控制台可以集中运行，设备服务按实际连接、SDK 环境与实时性要求部署在接入主机。公共契约是共享接口规范；设备运行时拥有生命周期，通过驱动访问硬件。

### 多机部署：轻量总台 + 算力节点 + 设备接入节点

目标是由一台**无需 GPU 的普通主机**运行总台，实验室其他机器按角色接入。中央 Agent Harness 在总台维护任务和工具循环，推理请求交给 5090 等算力节点；机械臂与相机的设备连接和本地循环留在接入机器。总图的层内文字标出部署角色，底部的主机标签对应具体逻辑层；图中机器是目标示例，不是当前在线清单。

| 部署角色 | 承载内容 | 依赖与边界 |
| --- | --- | --- |
| 轻量总台 | L1 工作台与终端、L2 应用/任务/用户会话、L3 Harness 编排、L4 目录与资源协调；任务元数据和审计 | 需要 CPU、内存、存储与网络，无需本地 GPU 或设备 SDK；模型权重由算力节点加载 |
| 算力节点 × N | L5 模型推理服务及按模型适配的 RTC 采样，各自环境与权重 | 登记模型、版本、能力、端点与健康；独立加载和调用，在线策略经控制会话提交目标 |
| 设备接入节点 × N | L5 观测调度与动作块执行器，L6 感知/执行运行时与机械臂内核，L7 驱动，连接 L8 硬件 | 节点服务对外提供能力入口，内部复用本机客户端与驱动；设备所有权、周期控制和最后一道约束留在本地 |

角色不等于固定物理机数量：5090 可以同时接机械臂和提供推理服务，一台接入机也可以管理多个设备实例。移动机器人可用机载电脑接入；USB/CAN/串口设备由其接入电脑代理，具备网络 API 的装置也可由网关适配，不要求所有硬件直接连接总台。硬件 SDK、控制环境与模型环境按实际角色安装，轻量总台应能在未安装这些可选环境时启动。

**有线 Mesh 物理拓扑。** 按用户提供的同款中兴巡天 ZXHN E2631 方案，主节点分别连接 Ubuntu 总台和两个 Mesh 子节点：A 就近接 5090 与机械臂接入机，B 接感知及其他设备接入机。主节点 LAN 至子节点 WAN 用作有线回程，沿用原生 Mesh 模式，具体端口角色及配对步骤以这批机器的固件为准。后台确认实际回程和主机互通，为服务保留稳定地址；图示不是已经接通的现场清单。

总图上方按逻辑层表达服务协作，底部以紧凑拓扑表达物理连接，两者通过部署角色和层号对应。网络拓扑不是额外的 L9，也不意味着所有业务调用按网线经过的设备依次处理。Mesh 主节点负责网络；Ubuntu 总台上的应用才负责 Agent、目录与任务。图示接入机走网线，移动机载电脑最后一跳可选 Wi-Fi；路由器之间保持有线回程。节点认证、设备控制权和物理设备生命周期不由 Mesh 配网代替。

**接入流程。** 首先显式配置总台地址与节点身份；节点经过认证后登记 `host_id`、设备实例、能力、端点、版本和健康，并持续更新状态。总台按实例定位服务，确认可达、获得授权与控制会话后再调用。节点在线、观测新鲜和具备控制权分别显示；设备上线不会自动使能。可使用可路由的受保护端点，无法直连时需配置认证双向通道或中继；登记本身不解决网络可达性。

**通信分工。** 总台协调任务、模型调用、授权和状态汇聚；设备与算力节点按授权订阅观测、传递策略目标。高带宽视频和逐帧策略数据不要求经总台中转，网络条件需要时可使用中继。原始数据先在设备侧采集或缓存，按任务写入选定存储；总台维护索引、轨迹引用和结果关联，不承担所有原始视频存储。

**失联与恢复。** 连续目标使用序号、有效期和租约，由设备侧判断过期并停止或保持。离散动作按能力声明的失联策略继续或取消，结果不确定时明确报告并对账。重连不自动恢复控制权或重放未知结果的动作。各主机 `monotonic` 时钟不可直接相减，远程协议需定义时间域、观测年龄和本地有效期检查，不能仅将 Unix socket 换成 TCP。算力节点离线应不影响独立的人工控制与设备查询；总台失联时，设备本地约束仍持续工作。

**现有启动方式。** 当前入口没有限定 RTX 5090 型号，但部署与通信主要按同一台 Linux 主机构建。另一台普通电脑访问现有网页可作为远程操作入口，实际应用服务和设备仍在原主机；这与迁出独立总台是两个阶段。

| 当前实现依据 | 对多机迁移的影响 |
| --- | --- |
| [run.sh](../../run.sh) 转交 Python 启动器；[bench.py](../../src/embodied/applications/workstation/bench.py) 使用本机 tmux，并按本机 boot ID/PID 选择最新 ready 内核 | 启动配置需按总台、设备与算力角色拆分；设备选择从“本机最新运行”改为明确实例 |
| [ControlClient](../../src/embodied/contracts/runtime/control.py) 读取本机运行文件、boot ID 与 `commands.sock`；[RPC](../../src/embodied/contracts/rpc.py) 和 [RuntimeReader](../../src/embodied/contracts/runtime/client.py) 使用 Unix socket | 保留本地控制边界，设备侧补受认证的远程能力入口；跨机身份、时效、取消与断线语义需独立验收 |
| [相机客户端](../../src/embodied/devices/sensors/client.py) 与 [transport](../../src/embodied/devices/sensors/transport.py) 使用本机 socket / IPC 帧与单调时钟 | 增加跨机流描述、网络订阅和时间质量信息，不能跨机共享原有 socket 路径 |
| [π0.5 worker](../../src/embodied/policy/pi05_zeroshot/worker_client.py) 依赖本机子进程/文件；[策略入口](../../src/embodied/policy/kernel_runner.py) 直接使用本机相机与控制会话 | 分离模型启动、观测传输、推理与设备动作执行，按契约连接远程模型服务 |
| [GR00T PolicyClient / ModelServer](../../src/embodied/policy/groot/policy.py) 已有 TCP 客户端，但默认服务仍在本机启动并使用 loopback | 网络调用边界可复用，仍需补远程端点配置、认证、健康与生命周期，不能当作完整多机能力 |

这些是已核对源码后的部署目标。本轮不改变 `./run.sh` 的启动行为，也不提供尚不存在的总台/节点启动命令；多机软件与实际节点接入仍需实现和验收。

### 中央 Agent Harness

Harness 维护上下文、任务状态、工具执行循环、会话检查点和事件追踪。模型是可替换的推理组件：可以使用 LLM / VLM 做任务规划、使用 VLA 或确定性算法完成特定技能，但模型不直接持有设备 SDK。现有策略入口和脚本任务提供复用基础，中央 Harness、统一场景状态与跨设备技能仍是待建设目标。

中央指统一任务上下文与调用协议的逻辑角色，可按会话或任务隔离运行，不要求整个平台只有一个进程。连续 VLA 策略可以作为受 Harness 监督的独立推理循环，通过控制会话提交带有效期的目标，不逐帧重新调用中央 LLM；设备侧继续执行租约、来源仲裁和本地约束。

上下文包括用户目标、会话记忆、场景引用与设备状态，观测保留时间、坐标系、来源和质量。原始视频按需采样或引用，不无界写入语言模型上下文。技能接口分别表达查询、订阅和动作，返回操作 ID、进度、结果、取消与真实错误；“工具请求受理”不等于“物理动作完成”。

恢复 Agent 检查点时先核对设备状态、任务结果和资源租约。检查点恢复的是计算状态，不能自动重放执行结果不确定的运动。任务编排可以调用子 Agent 或模型插件，但不要求一开始就建立多 Agent 集群。

### L5 推理部署与策略运行

本层连接模型与实际动作，按职责分工而不要求部署在同一台主机。总台上的 Harness 负责模型调用、策略技能启停和结果监督；连续策略在独立会话内运行。人工和确定性动作可直接调用设备能力，不需要经过 VLA 推理。

| 模块 | 部署位置 | 对接内容 |
| --- | --- | --- |
| 观测与异步调度 | 设备侧客户端，靠近观测与执行进度 | 适配图像/状态、单位、坐标系与新鲜度；携带观测版本、执行步号、剩余前缀与延迟信息，有界调度请求 |
| 模型服务与 RTC 采样适配 | 5090 等算力节点 | 独立加载环境、权重和模型版本；提供健康与推理接口；兼容策略按前缀与延迟条件生成动作块 |
| 动作块执行器 | 设备接入机 | 维护缓冲和实际执行游标，对齐并接纳新块、丢弃过期区段，经控制会话下发有效目标 |
| L6 设备运行时 | 设备接入机 | 维持本地周期控制、资源租约、来源仲裁、限位、停止及真实反馈 |

这里的 RTC 指 **Real-Time Chunking**。原始推理时方法在执行当前动作块期间异步生成下一块，通过扩散/流模型采样约束推理期间将执行的前缀，并对其余重叠区施加引导，使后续动作与已承诺轨迹相容。它涉及模型采样适配，普通动作队列、拼接、插值或输出后平滑不能自动等同于 RTC。参考 [PI 官方说明](https://www.pi.website/research/real_time_chunking) 和 [论文 §3 / Algorithm 1](https://www.physicalintelligence.company/download/real_time_chunking.pdf)。本设计采用这一推理时版本作为研究依据；其他训练时变体应单独标明。

[OpenPI 远程推理文档](https://github.com/Physical-Intelligence/openpi/blob/main/docs/remote_inference.md) 可借鉴模型服务与轻客户端的部署边界，但返回 action chunk 的普通接口不代表完整 RTC。每个模型适配需明确可否约束采样前缀，不能仅在黑盒输出外加一个队列就声明支持。观测适配、网络协议、健康与指标是工程交付职责，不能都归作论文算法。

当前可复用的代码包括 [kernel_runner.py](../../src/embodied/policy/kernel_runner.py) 的观测和动作校验、[GR00T PolicyWorker](../../src/embodied/policy/groot/policy.py) 的客户端和异步 worker，以及 [groot/runtime.py](../../src/embodied/policy/groot/runtime.py) 的动作排时、队列与重叠融合。后者虽然含 `RTC_MAX_OVERLAP_STEPS` 命名，其实现是输出后融合；[groot/kernel_runtime.py](../../src/embodied/policy/groot/kernel_runtime.py) 仍在队列为空时提交下一次推理。它们是复用基础，尚未形成论文式前缀采样与连续执行协同。

工程上需关联模型/契约版本、观测时间域、序号、动作步长、执行游标和会话；端到端延迟包含采集、预处理、网络、排队和推理。延迟超限、缓冲欠载、旧响应、撤权与人工接管需要明确失效处理。RTC 不能消除任意网络延迟，也不替代设备控制约束。验证先使用仿真和回放，记录响应与实际执行轨迹，再进行对应设备的连续动作验收。本轮只增加架构和交付边界，不运行或实现 RTC 算法。

### 语音、手势与人工接管

语音输入经可替换 ASR 转为文本/候选意图，统一会话将目标交给 Harness，结果可通过 TTS 反馈。语音层管理轮次、打断与音频流；取消播报与取消设备动作使用不同协议。当前定向检查未发现 ASR / TTS 实现，语音明确标为规划接入。

手势既可以表达离散任务，也可以产生连续位姿目标。离散任务进入 Harness，连续目标经控制会话携带来源、租约与短 TTL 直接进入设备运行时，不逐帧经过 LLM。人工接管需要明确暂停任务与转移控制权，不能让两个来源同时写同一执行资源。

现有浏览器手势已在 [teleoperation/runtime.ts](../../apps/console/src/features/teleoperation/runtime.ts) 使用 MediaPipe 手部识别、离合和夹爪映射；[console/kernel/arx.py](../../src/embodied/applications/console/kernel/arx.py) 经 `ControlSession` 提交目标。当前是机械臂适配，通用手势插件和跨设备交互会话尚待补齐。历史设计中的“手势待迁移”不能覆盖较新的源码与 [客户端计划实施记录](../plans/03-kernel-clients.md)。

### 机械臂运动控制核心

机械臂内核单独展开，复用现有 [gateway.py](../../src/embodied/control/gateway.py)、[commands.py](../../src/embodied/control/commands.py) 与 [worker.py](../../src/embodied/control/worker.py)。离散动作可先预览并由 `MotionPlanner` 生成 MoveJ / MoveL / Path 轨迹，再交给调度；连续遥操目标直接进入有界命令路径，不必每次经过轨迹规划。

周期 worker 读取设备状态，通过 `CommandEngine` 执行租约、来源仲裁、轨迹采样和停止/反馈约束，调用驱动并发布 `RobotTick`。只读 observer 对外提供状态，工作台和 Agent 均不接管周期循环。网络请求、语音识别和模型推理不进入这条本地实时路径。新版真机仍待完整验收，原生 Quest 与 RPC 检查路径的差异继续保留在详情中。

移动机器人保留底盘/导航运行时，其他实验装置通过自己的能力插件接入；相机与传感器不需要实现机械臂动作接口。设备身份关联它们的观测与动作，执行结果直接反馈 Agent，不以视觉识别作为动作结束的唯一判据。

### 分工与接口交付

| 协作边界 | 交付内容 |
| --- | --- |
| L1 交互呈现 ↔ L2 应用服务 | 用户身份、目标、来源、会话、进度和回答；各客户端共享业务语义 |
| L2 任务管理 ↔ L3 Harness | 任务 ID、提交、取消与结果；应用任务状态、Agent 执行状态分别维护并关联 |
| L3 Harness ↔ L4 技能/工具 | 类型化输入输出、操作 ID、结果、取消、状态和错误 |
| L4 能力接入 ↔ L5 策略运行 / L6 设备能力 | 解析实例和端点、申请控制权；实际执行方检查权限、租约、有效期和本地约束 |
| L5 推理服务 ↔ 策略执行器 ↔ L6 设备运行时 | 观测版本、动作步号、前缀、延迟、动作块与执行游标；有效目标经控制会话下发 |
| L6 设备运行时 ↔ L7 驱动适配 | 按领域契约连接、读状态、写命令和关闭；设备 SDK 与型号差异留在驱动 |
| L6 感知/执行 → 上下文、模型与数据 | 实时观测与状态通过订阅消费；Agent 轨迹与原始实验数据分别维护并关联 |
| 跨层服务 ↔ 各使用方 | 可替换模型、通信、身份与审计、插件装配、托管与故障清理 |

## 层次与职责

| 层次 | 职责 | 依赖边界 |
| --- | --- | --- |
| L1 交互呈现层 | 独立网页、CLI / TUI、语音与手势输入；展示设备、观测、任务与反馈 | 只适配输入输出，通过 L2 公共服务表达业务意图；不持有设备 SDK |
| L2 应用服务层 | 统一应用 API、用户会话与人工接管、任务与实验管理 | 受理用户请求并关联任务、身份与进度；将智能任务交给 L3，将人工控制交给 L4 |
| L3 智能编排层 | 中央 Agent Harness 的规划与执行监督、上下文与环境状态、检查点与轨迹 | 调用模型和 L4 技能工具；不接管设备周期控制，不把工具受理当作动作完成 |
| L4 能力接入与契约层 | 技能/工具适配、公共能力契约、设备实例与能力目录、资源与控制会话 | 按能力解析端点和请求控制权；共享契约不拥有设备或转发请求，目录不等于插件注册表 |
| L5 推理部署与策略层 | 模型实例与推理服务、观测适配与异步调度、RTC 采样适配、动作块缓冲与对齐 | 算力端推理与设备端执行协同；仅策略路径经过，人工/确定性技能可直接调用设备；RTC 按模型适配 |
| L6 设备运行时层 | 感知流生命周期、机械臂运动内核、移动执行与其他装置运行时 | 持有设备生命周期与本地循环，执行最终租约/来源/有效期与领域约束；通过 L7 访问设备 |
| L7 驱动适配层 | 相机/传感器、机械臂、底盘/装置的厂商协议与模型插件 | 封装 SDK、协议、初始化、读写与关闭，依赖稳定领域契约，不依赖工作台或 Agent |
| L8 硬件与设备层 | 相机与传感器、机械臂与夹爪、移动机器人与实验装置，或对应仿真替身 | 物理实例可组合感知与执行能力；不强制所有设备实现同一种动作接口 |
| 跨层：模型与数据服务 | 模型/算法定义、权重与契约、实验数据与资产 | 实例服务由 L5 装配；按接口服务 L2—L6；在线推理订阅观测，数据服务旁路记录，不串入设备实时周期 |
| 跨层：基础设施 | 网络与通信、安全权限、插件注册装配、部署与运维 | 通信与服务定位、强制授权与审计、实现装配、独立托管分别交付；最终设备约束仍在 L6 |

机器人内核是“机械臂能力运行时”，不再承担整个实验室的通用设备内核职责。相机、底盘和传感器不进入机械臂 `worker`，不必实现 `RobotBackend.step(ControlCommand)`。

公共契约是共享接口与 schema，不拥有设备、不转发请求，也不额外建立中心进程。主图箭头表示主要交互，模块详情分别说明已有基础与待建设内容；主图中的分组和连线不表示全部能力已经实现。

网络、安全和运维是横向支撑各服务的基础设施，在图中单独分组，不是所有设备请求依次穿过的串行中转层。插件治理管理实现和装配，与这些基础设施分别维护职责。

## 网页、终端与公共应用服务

网页和终端需要分别维护。网页面向设备视图、可视化与任务交互；终端面向命令、参数、脚本自动化与文字状态。两者都调用公共应用服务，实验步骤、动作语义、设备状态机和取消逻辑只维护一份。

```text
L1 网页 / 终端 / 语音 / 手势
             ↓
L2 应用 API + 用户会话 + 任务管理
             ├─ 智能任务 → L3 Harness ─┐
             └─ 人工控制 ──────────────┤
                                      ↓
                         L4 能力接口 + 控制会话
                           ├─ 策略技能 → L5 推理与执行器 ─┐
                           └─ 直接设备能力 ──────────────┤
                                                         ↓
                         L6 设备运行时（本地校验与执行）
                                      ↓
                         L7 驱动适配 → L8 硬件
```

视图插件负责呈现和交互，命令插件负责参数解析和输出，业务插件负责实验与操作。它们共享契约，不互相导入私有实现。新增一种设备能力时可增加相应视图和命令适配，不在两个入口里各写一套执行逻辑。

终端可以显式请求启动、停止或重启服务，但进程托管与设备生命周期属于应用/运维服务。关闭窗口或刷新网页不代表停止设备，也不能让设备失去唯一所有者。前端隐藏按钮或终端参数校验不能替代服务端权限检查。

当前已有独立 Vue 控制台、监看页和 `./run.sh` / tmux / Rich 终端；其业务入口和部分进程装配仍需按上述边界继续收敛。本设计没有把它们描述成已经完成实验室级统一入口。

## 网络、安全与运维基础设施

### 网络与通信层

网络接入明确主机、监听地址、受控入口及连接质量；服务定位负责将已登记能力解析为端点；传输插件负责管理请求、状态事件与大流量数据。设备实例目录回答“是什么设备、归属哪里”，服务端点目录回答“从哪里访问”，插件目录回答“用哪个实现”，三者不能混为一张注册表。

网络传输与硬件协议也分别维护。即使某个设备通过网络连接，厂商协议解码、初始化和动作语义仍归驱动；网络层只负责连接和消息传输。网络恢复不自动取得控制权，也不能无条件重发运动命令。

现有基础包括本机 Unix socket RPC、控制台 Tailscale / LAN 部署、HTTPS 与 WebRTC 等通道。它们是局部实现，尚未构成通用多主机服务发现、路由或网络治理。平台不要求所有设备绑定一种远程协议。

### 安全与权限层

| 职责 | 回答的问题 | 执行位置与边界 |
| --- | --- | --- |
| 身份与权限 | 谁可以查询、订阅或控制哪些能力？ | API 及实际受保护服务端强制检查，不能只放在网页或终端 |
| 资源占用与租约 | 此刻谁拥有这个资源？ | 资源所有者与对应能力运行时；租约不替代身份权限 |
| 设备侧安全约束 | 当前反馈与约束下，这个动作能否执行？ | 设备侧运行时的限位、输出许可、有效期与停止逻辑；权限和租约均不能绕过 |
| 凭据与审计 | 如何建立认证通信，如何追溯实际操作？ | 凭据提供方、服务与审计输出；保留身份、目标、请求 ID、授权与执行结果 |

身份提供方、授权策略、凭据提供方和审计输出可按接口扩展，但强制校验位置不能变成可随意关闭的插件选项。设备安全策略按能力适配，最终执行仍在本地运行时，不依赖一次远程网络调用才能限制危险输出。软件停止与硬件急停分别设计、分别验收。

控制台已有配对令牌、本地证书与加密通信基础；统一用户/服务身份、能力级授权、凭据生命周期、操作审计及跨设备安全约束仍待建设。Git 贡献记录只反映代码变更，不能冒充设备操作审计或安全验收。原生 Quest 与 RPC 的工作区检查差异继续如实保留。

### 部署配置与可观测性

部署、环境与进程监督独立于两个交互入口；实例配置、运行环境与凭据引用分别管理。每个服务报告健康、日志、指标、错误及时间基准质量，由运维能力汇聚。时间同步只能提供带质量信息的基准，不能把网络连通视为时钟已同步。

复用现有工作台与环境管理，逐步把托管语义从终端呈现中分离。故障、取消和退出路径保留真实结果，并清理已创建的设备、连接和资源；不能因某个面板退出而失去这些职责。

## 插件化与解耦规则

1. **接口与实现分开。** 公共契约定义可观察行为，插件负责实现；应用按能力使用设备，不以型号名称决定调用链。
2. **插件与实例分开。** 插件目录记录实现、入口、版本与环境；设备目录记录实验室实际设备。同一个插件可以建立多个设备实例，每个实例各自拥有身份、连接、状态与资源。
3. **共享基础，保留专业接口。** 所有设备共享描述与基础生命周期；动作、图像流、底盘运动、测量等按能力定义类型化接口。只读传感器没有动作方法也能接入。
4. **能力允许组合。** RGB-D 相机可以同时提供 RGB、深度、内参与 IMU；移动机器人可以组合底盘、定位和相机能力。设备类别用于导航，不能替代能力检查。
5. **装配集中。** 配置选择实例、插件、运行环境及服务端点；使用现有 Registry 演进，不再平行增加第二套工厂注册表。
6. **插件不等于微服务。** 只有设备独占、SDK 依赖冲突、实时性或故障隔离需要时才增加进程。纯算法与格式转换可保留为库插件。
7. **插件不依赖具体同伴。** 通过契约声明所需能力，在装配时解析；禁止直接导入另一个设备插件的私有实现。算法不反向导入实验组织代码。
8. **加载、连接、使能分开。** 查询插件目录或验证配置不打开设备；设备上线不取得控制权；重新连接不自动恢复动作或重放旧命令。
9. **交互入口与业务分开。** 网页、CLI / TUI 是不同客户端，共享应用服务与实验逻辑；设备进程生命周期不依赖界面窗口。
10. **基础设施与强制规则分开。** 网络、认证、审计和运维实现可扩展；实际受保护能力的权限检查、资源互斥与设备约束不能通过更换插件绕过。

插件类型按真实扩展点逐步增加：设备驱动、能力适配、传输、算法/模型、实验步骤、采集/导出、界面视图。当前并非每一类都有可用工厂，不为没有实际需求的类型登记空实现，也不预设热更新或远程安装机制。

## 最小公共契约

### 设备实例与插件声明

| 对象 | 最小字段或语义 |
| --- | --- |
| 插件声明 | `plugin_id`、种类、实现入口、插件版本、契约版本、运行环境、依赖、提供的能力 |
| 设备实例 | `device_id`、名称、类别、`driver_id`、驱动版本、`host_id`、位置、连接配置引用、能力列表、流列表、资源标识 |
| 能力描述 | `capability_id`、版本、输入输出 schema、单位、坐标系、约束、是否改变设备状态、取消与超时语义 |
| 服务定位 | 实例/能力到服务端点的映射，以及所属主机和更新时间；具体传输由部署选择 |
| 配置边界 | 型号参数由驱动解释，连接地址和秘密留在部署配置；公开描述只携带必要引用 |

`device_id` 标识设备实例，不能用易变端口或插件名称代替。插件版本与能力契约版本分别记录。具体驱动仅实现它声明支持的能力，消费者在实验开始前检查兼容性。

### 生命周期与状态

基础生命周期表达“描述 → 显式连接 → 健康检查 → 关闭”；发现是可选插件能力，先实现人工登记，再增加实际协议支持的发现方式。

状态分别表达：是否登记、连接阶段、健康/故障、观测是否新鲜、资源是否被占用、调用者是否持有控制权。每类状态附更新时间与错误原因。进程存在、端口连通、设备出数据和可执行动作不能互相替代。

设备服务拥有连接并负责失败清理。一个实例连接失败不应拖垮其他设备；关闭失败保留真实错误。重连可恢复观测，但恢复输出需要重新满足许可、租约和领域运行时条件。

### 命令、状态事件与数据流

| 通道 | 内容与规则 |
| --- | --- |
| 管理与控制 | 查询描述、连接管理、申请/释放资源、能力命令、取消；携带来源、请求 ID、租约/有效期、状态与错误 |
| 状态与事件 | 连接变化、故障、控制权变化、操作完成/失败；区分请求已受理与实际执行完成 |
| 观测数据 | 图像、遥测、测量；携带设备/流 ID、序号、采样时间、接收时间、时间基准、单位、坐标系、质量与缺失信息 |

控制面不转发所有大流量数据；相机和时序流可使用适合自身吞吐的传输。平台不在此阶段规定所有设备必须走 ROS、某个消息总线或单一网络协议。

机械臂或底盘的实时执行与最后一道约束检查留在设备侧运行时。网络请求只提交有期限的目标或动作，不用网络心跳替代实时控制循环。数据消费者不能通过订阅接口取得执行权。

## 设备接入细节

下面四类设备用于明确接入与验收范围，主图仍按感知和执行能力组织。机械臂状态与移动机器人里程计可以参与状态估计，但动作完成、失败和故障反馈仍由执行运行时直接上报。

| 设备 | 主要能力 | 需要单独验证的部分 |
| --- | --- | --- |
| 机械臂 | 状态反馈、关节/笛卡尔动作、夹爪、停止；按设备声明可选能力 | 关节数、单位、运动学、限位、停止与断连行为；现有 X5 新版真机内核仍待完整验收 |
| 相机 | RGB/深度等帧、内参、时间戳、按需曝光与触发 | 帧格式、丢帧、同步、设备独占、多个订阅者；已有 RealSense / synthetic 基础 |
| 移动机器人 | 底盘速度/目标、里程计；可选定位、导航与停止 | 坐标系、速度约束、导航取消、断连停车、定位质量；型号和适配协议尚待选择 |
| 传感器 | 标量/向量/时序观测、事件；可选采样配置、触发或校准 | 单位、量程、采样时间、有效性、延迟和校准来源；需要选定真实设备验证 |

Quest、iPhone 等作为控制输入插件，可以映射到支持的能力；输入设备不拥有目标设备 SDK。机械臂的原生 Quest 路径与 RPC 路径保留其真实约束差异，不把现有行为写成所有设备已统一通过相同检查。

## 资源与实验编排

相机可以由一个服务持有设备、多个消费者共享读取；机械臂和底盘输出按实际资源互斥。当前 `DeviceLease` 是本机文件锁，机器人租约也有自身范围，不能直接当作分布式设备调度。

通用实验步骤声明所需能力和资源，由装配层选择设备实例。执行前检查能力兼容性与必要状态，按确定顺序申请资源，申请失败释放已获得资源；执行中记录部分成功、失败、取消与关闭结果。多设备步骤不承诺物理动作可以原子回滚。

跨主机扩展时，需另行实现服务认证、租约有效期和撤权、重复请求处理、连接中断的本地停止规则。状态汇聚不能代替接入主机的实际资源所有权。多机时间对齐应记录时钟来源与误差，不把软件时间戳宣称为硬件同步。

## 现有基础与缺口

| 现有基础 | 可以复用 | 尚缺的实验室能力 |
| --- | --- | --- |
| `contracts/registry.py` | 显式工厂、按需加载、运行环境与 API 版本检查 | 通用插件声明演进；设备实例目录不在此类职责内 |
| `contracts/interfaces.py` | 机器人、相机、输入、规划等专业接口 | 跨设备身份、能力 schema 与状态/生命周期契约 |
| `control/`、`devices/robots/` | 机械臂运行时、驱动、模型与仿真 | 新设备类别各自的运行时，非通用化当前 worker |
| `devices/sensors/` | 独立相机所有者、共享帧与工厂 | 通用传感器测量、事件和设备协议适配 |
| `applications/workstation/` | 本机服务装配与现有工作台 | 总台/设备/算力角色拆分、多设备实例展示、服务定位、多主机管理 |
| `apps/console/`、`applications/console/` | 独立网页、版本化 API、局部配对令牌/HTTPS/WebRTC | 统一应用服务、能力级授权、实验室通用前端与网络治理 |
| `apps/console/src/features/teleoperation/` | 浏览器手势、离合、夹爪映射与短 TTL 控制接入 | 通用手势插件、跨模态交互会话；语音 ASR / TTS 尚待建设 |
| `run.sh`、工作台终端 | CLI / TUI、命令发现、状态与日志入口 | 命令适配与托管解耦，和网页共享完整业务语义 |
| `data/`、`policy/` | 采集、导出、策略环境、GR00T TCP 客户端与动作队列 | 模型服务独立部署、网络观测与异步策略、论文式 RTC 采样适配及设备侧执行协同 |
| 现有操作、任务与策略入口 | 可作为 Harness 调用的技能基础 | 中央 Agent、场景上下文、工具目录、会话检查点与恢复 |

旧执行入口与迁移中的生命周期保持如实标注；本设计不删除旧链路，也不改变真机动作。

## 推进顺序与验收依据

1. **轻量总台与节点角色分离。** 沿用现有启动入口与环境管理，分开总台、设备和算力启动配置。总台在没有 CUDA、模型权重、设备 SDK 的主机上可启动；服务生命周期独立于网页和终端。
2. **两台主机的最小接入闭环。** 实现显式节点登记、实例目录与设备侧认证能力入口，内部复用现有本地客户端。先让无 GPU 总台连接另一台主机上的仿真与相机服务，按实例查询、订阅、操作和取消；验证请求 ID、授权、跨机时效、失联过期和重连不重放。
3. **推理部署与策略执行。** 分离模型服务启动和调用，复用已有 GR00T 网络客户端边界，再拆分 π0.5 本机子进程/文件协议。验证远程观测订阅、推理结果经控制会话执行、模型离线与超时；算力节点退出后，人工控制与设备查询仍可用。对选定兼容策略再实现 RTC 前缀约束采样和设备侧缓冲对齐；验证延迟波动、旧响应、队列欠载、取消和接管，保存真实执行轨迹，不能只凭动作变平滑判定 RTC 验收完成。
4. **多设备与节点生命周期。** 登记多个主机与设备实例，补齐同驱动多实例、相机多订阅、资源互斥、部分失败清理、权限撤销、运维与审计。真机逐类验收，网络连通不替代运动和断连验证。
5. **中央 Harness 与多模态协同。** 从查询状态、订阅观测和可取消的仿真技能接入任务闭环，验证真实结果、检查点恢复与人工接管。将已有手势按统一会话收敛，再增加语音、移动机器人与传感器；连续策略不逐帧调用中央 LLM。

具体型号、协议、物理资源关系和验证场景在接入前确认。本轮只完善设计与可视化，不据此声称已经完成新硬件接入或现场验证。
